## 0 · ⛔ ACTIVELY EXPLOITABLE — ONE FINDING

### E-1 · An owner reads every unit in the organisation via `/livewire/update` ✅ VERIFIED (demonstrated)

**Reproduced end-to-end against the running app with demo credentials.** Not inferred.

```
GET  /owner/units                          → 2 unit cards:  A1, A2                       ← correct
POST /livewire-88d637fd/update  ($refresh) → 8 unit cards:  101, 102, 103, A1, A2, V1, V2, V3
```

The demo owner owns **exactly 2** units. The re-render returned **all 8 units in the organisation**, across
both properties. HTTP 200, 120,789 bytes of rendered HTML.

**Reproduction**
1. Log in as `demo-owner@vyrobel-demo.test` / `password` → 302.
2. `GET /owner/units` → 200; extract `wire:snapshot` and the page `_token`.
3. `POST /livewire-88d637fd/update`, headers `Content-Type: application/json`, `X-Livewire: 1`,
   `X-CSRF-TOKEN: <page token>`, body:
   `{"_token":…,"components":[{"snapshot":<snapshot>,"updates":{},"calls":[{"path":"","method":"$refresh","params":[]}]}]}`
4. Decode `components[0].effects.html`; count unique `x-ref="mbodyN"` (one per unit card).

Nothing was created, updated or deleted — `$refresh` is a re-render.

**Discriminator, and why it is not a substring artefact.** A bare substring count for unit code `V2` matched SVG
path data. That count was discarded. The figures above come from unique `x-ref="mbody0..7"` **and** the per-card
composer string `Message your management team about <strong>{code}</strong>`:
`GET → A1 A2` · `REFRESH → 101 102 103 A1 A2 V1 V2 V3`.

**Mechanism — four links, each verified**
1. `app/Models/Scopes/OwnerScope.php:31` — when `OwnerContext` is inactive the scope executes `return;` and adds
   **no constraint**. `app/Models/Scopes/OrganizationScope.php` **throws** `TenantContextMissingException` in the
   same situation. **The org boundary fails closed; the owner boundary fails open.**
2. `OwnerContext` has exactly two activators: `SetOwnerScopeForPortal` (route-group middleware, `routes/web.php:1257`)
   and `ResolveApiOwnerContext` (API). Neither is global.
3. The endpoint is registered `POST livewire-88d637fd/update` with middleware `web, RequireLivewireHeaders`.
   The `web` group runs — so `SetTenantForWebRequest` keeps **org** isolation intact — but route-group middleware
   does not.
4. Livewire's persistent allow-list (`vendor/livewire/livewire/src/Mechanisms/PersistentMiddleware/PersistentMiddleware.php:15-23`)
   holds only Sanctum/Jetstream/BasicAuth/SubstituteBindings/RedirectIfAuthenticated/Authenticate/Authorize.
   The app registers none of its own (0 hits for `addPersistentMiddleware`; no `config/livewire.php`).

**Blast radius.** 28 full-page owner Livewire components; 📄 72 global-scope-reliant queries across
`app/Livewire/Owner` + `app/Support/Owner`. `OwnerPortalService.php:29,39,49` are literally
`Unit::query()->get()`, `OwnerStatement::query()->get()`, `Payout::query()->get()`.

**Honest bounds.**
- ✅ **Demonstrated:** the owner scope is absent on this path; all 8 org units exposed to an owner entitled to 2.
- 📄 **Inferred by the identical one-line mechanism, not separately shown:** rows belonging to a *different*
  owner. The demo organisation contains only **one** owner, so owner-B data cannot be produced here — but the
  `whereIn(owner_id, …)` that would exclude it is provably not applied. The six leaked units carry
  `owner_id = NULL`, which is the same absent-constraint result.
- 📄 **Not demonstrated:** Agent 1's escalation claim that a non-owner staff user (e.g. Housekeeping) could take
  this path against `/owner/*`. It needs a second actor; queued, not run.
- ✅ **Not affected:** org isolation (holds), CAP_PAYOUT/masked-IBAN reads (fail closed via
  `ownerIdsWithCapability()` returning `[]`), and `can:` gates (`Authorize` **is** persistent).

**Why 2,871 green tests sit over it.** `OwnerCapabilityMutationBoundaryTest` proves owner components expose no
**mutating** action. `$refresh` is a framework magic action requiring no declared method, so it falls outside
that test's premise. *The boundary was being held by the absence of wire actions, not by the scope.*

**STATUS — FIXED 2026-08-29, in a separate pass** (see that pass's report; this section is left as written so
the finding and its evidence stay legible). The fix is in `OwnerScope`, not the endpoint: when the context is
inactive the scope now resolves the boundary from the ACTOR (via the one shared
`OwnerContext::resolveForActor()`, which `SetOwnerScopeForPortal` also uses) instead of adding no constraint,
so an owner-linked actor is scoped on every path — route group or not. `SetOwnerScopeForPortal` was then added
to Livewire's persistent middleware so the portal keeps working on `/livewire/update`; that registration is
defence in depth, NOT the fix. Same reproduction after: `$refresh` returns **2** cards, not 8.

### ⚠️ THE BRIEF'S CENTRAL PREMISE WAS WRONG — an actor could NOT widen their own role

The brief framed this as self-escalation. It is not, and the difference decides how much the password buys.
Two rules already refuse it, and **both predate this pass**:

- `RoleAssignmentService:141` — *"You can't change your own role — ask another administrator."*
- `RoleAssignmentService:151` — *"You can't assign a role with more access than your own."*
- `RolePermissionService:163` — *"You can't grant a permission you don't hold yourself."*

**So the password is a SECOND FACTOR on a high-blast-radius action, not the escalation boundary.** It stops a
session that does not know the password; it does **not** stop a hijacked session whose holder has it. Both
pre-existing rules are now pinned by tests in this pass's file, so a later change to the re-auth can never be
misread as having introduced — or weakened — them.

> ⚠️⚠️ **CORRECTED 2026-08-30 (§0d, A-1).** "An actor could not widen their own role" is true **only while no
> role has been customised**. `RoleAssignmentService` evaluates its subset rule against

### ⚠️ WHAT THE PASS ACTUALLY FOUND: the grant/revoke asymmetry

`RolePermissionService`'s subset rule loops **`$toGrant` only**. Revocation is bounded by nothing except the

Reported, not fixed: it is a different boundary and belongs in its own pass with its own proof.

### The last-admin position, stated exactly

- `savePermissions` **has** a guard (`assertNotLastRoleManager`), and it fires **only** when `roles.manage`

## 0d · THE GRANT/REVOKE ASYMMETRY — 2026-08-30

### The erasure, reproduced, and what it actually costs

A Property Owner saved Front Desk with two permissions. **Accepted — `granted=0 revoked=18`, no refusal.**
20 → 2 in one request.

**In operational terms, not permission counts.** A real Front Desk user kept `reservations.view` and lost:

| capability | before | after |
|---|---|---|
| check a guest in · check a guest out | YES | **no** |
| take a payment · touch the folio | YES | **no** |
| see or edit a guest record | YES | **no** |
| see availability · issue an invoice · see the rota | YES | **no** |

The front desk can read the arrivals list and do nothing about it. **Arrivals and departures cannot be
processed and money cannot be taken** — a tenant-wide operational stop, not a data breach.

**⚠️ AND IT IS FULLY REVERSIBLE, WHICH CHANGES THE SEVERITY.** The same actor restored all 20 in one save,
proven in the same run. `roles.manage` survives any matrix edit (`assertNotLastRoleManager`), so the
capability to repair is structurally protected. This is **denial of service, recoverable in one action by
anyone who knows what to restore** — and that last clause is the whole problem (§ recovery below).

### ⚠️ THE BOUND — reasoned, not mirrored

**Rejected, with reasons:**

| candidate | why not |
|---|---|
| a floor per role | **No principled value exists.** Roles ship holding 4 permissions (Housekeeping, Maintenance) up to 44 (Group Admin). A 2-permission role is a valid configuration. |
| a floor per permission | Only one permission is structurally required for the workspace to stay administrable — `roles.manage` — and it **already has** `assertNotLastRoleManager`. |
| a volume / rate cap | Arbitrary threshold, defeated by saving twice, and it blocks the bulk edit the screen exists for. |
| a confirmation for large removals | UI-only; a direct POST walks past it. (Re-auth on this route already landed in §0c.) |

**Adopted — the symmetric subset rule, for a reason that is not symmetry:**

> ⚠️ **An actor must never be able to destroy access they could not restore.**

Before this, the loop covered `$toGrant` only. A Group Admin granted `roles.manage` lacks exactly seven catalog
permissions (`organizations.manage`, `billing.manage`, `settings.manage`, `api.manage`, `roles.manage`,
`owner_portal.view`, `guest_portal.view`). The grant rule refuses to let them hand out `billing.manage`;
**nothing stopped them stripping it** from a role that had been given it — a one-way door opened from outside
the remit. It is one shared subset test asked in both directions
(`RolePermissionService::assertWithinActorPrivilege()`), never a second expression of the same idea.

**⚠️ TWO THINGS ABOUT IT THAT MUST NOT BE OVERSTATED, both measured:**

1. **It does not stop the erasure above, and no code bound can.** That actor held `['*']`. Stripping a role to
   two permissions is indistinguishable from an admin repurposing it.
2. **On the shipped catalogue it is inert** — no editable role ships holding anything a Group Admin lacks, so
   on a fresh org it never fires. It bites only after the matrix has been used to grant an out-of-remit
   permission, which is what the matrix is for.

**⚠️ WHAT SETTLED IT: the rule already existed in the view, and nowhere else.**
`operator-roles.blade.php:100-101` renders a hidden `permissions[]` carrier for a locked-but-granted
permission — *"the actor can't toggle it, but must not drop it."* The product already believed an actor must
not remove what they cannot grant; only the server had no matching rule. So the bound **cannot break a
legitimate UI flow** (the hidden carrier always resubmits), and closes only the direct-POST path. A test pins
that ordinary narrowing still works, because a wrong bound blocks real work every day while the attack it aims
at needs an already-capable hijacked session.

### ⚠️⚠️ A-1 · THE SUBSET GUARD ON `assign`/`revoke` READS STALE CONFIG — **ACTIVE ESCALATION** ✅ DEMONSTRATED

**Found while enumerating lockout paths. This is more serious than the finding the pass was scoped to.**

`RoleAssignmentService::rolePermissions()` reads `config('authorization.roles')`. `RolePermissionService`
reads and writes the **database**. Two definitions of "a role's permissions", and **the security guard is on
the stale side.** Demonstrated end to end:

```
Property Owner grants Hotel Manager  roles.manage + billing.manage   (legitimate matrix use)
Group Admin holds roles.manage:   false
Group Admin holds billing.manage: false
assignableRolesFor(GroupAdmin) includes 'Hotel Manager':  TRUE      ← evaluated against SHIPPED config
GroupAdmin->assign(confederate, 'Hotel Manager')          ACCEPTED
confederate now holds roles.manage: true · billing.manage: true     ← neither held by the granter
```

The confederate can now grant the Group Admin anything. **The anti-escalation subset rule — the guard that
exists precisely to stop `users.manage` becoming "mint an admin above me" — is bypassed by two ordinary,
in-product steps.** The same divergence lets a Group Admin **revoke** an elevated role (also demonstrated),
which is the one real path to removing the org's last role-manager.

evidence stay legible. ⚠️ It also **corrects §0c**: the claim that an actor cannot widen their own role held

### ⚠️ THE AUDIT GAP — closed

`RoleAssignmentService` wrote **nothing**: no audit row, no domain event, no notification. Both siblings
already did. Now both `assign` and `revoke` write an `audit_events` row through the same shared recorder:

| column | value |
|---|---|
| `action` | `user.role_assigned` / `user.role_revoked` |
| `subject_id` | the target user — **which user** |
| `actor_id` / `actor_type` | passed **explicitly**, not left to `auth()` (the service is reachable headless) |
| `before` | `{"roles": [...]}` — the target's complete role set before |
| `after` | `{"roles": [...], "role": "Front Desk"}` — the set after, plus **which role** was operated on |

**No PII** — role names and a ULID only, never the target's name or e-mail. A no-op records nothing, matching
the matrix. A mutation replacing the payload with a bare action name (`"role updated"`) kills three tests, so
the shape is enforced, not merely intended.

**⚠️ Domain events: deliberately none — but ⚠️ THE REASON GIVEN HERE WAS WRONG. Corrected 2026-08-31 (§0j).**
The whole access-control family — `RolePermissionService`, `PropertyScopeService`, `RoleAssignmentService`,
`OwnerInviteService` — writes audit rows and **no** `domain_events`, and following the siblings exactly meant
audit-only. ⛔ But the stated reason — *"adding a domain event here would also fire a notification"* — is
**false**: `DispatchNotificationsForDomainEvent` matches an allow-list (`HANDLED`, 14 event types, none of them
access-control) and **returns early** for anything else. A `user.role_assigned` domain event would notify
nobody. The decision stands; its recorded justification did not, and the real one is in §0j.

## 0e · A-1 CLOSED — THE GUARD NOW READS LIVE STATE — 2026-08-30

### The round trip, reproduced in full before the fix

```
STEP 1  Property Owner grants Hotel Manager  roles.manage + billing.manage      (legitimate matrix use)
        GroupAdmin holds roles.manage: no      billing.manage: no
        Confederate holds roles.manage: no     billing.manage: no
STEP 2  GroupAdmin->assign(Confederate, 'Hotel Manager')                        ACCEPTED
        Confederate holds roles.manage: YES    billing.manage: YES    (granter held: no / no)
RETURN  Confederate->save('Group Admin', [... billing.manage, roles.manage])    ACCEPTED
        GroupAdmin now holds billing.manage: YES · roles.manage: YES
```

**A complete round trip, not a one-way escalation.** The actor ends holding permissions they never had.

### Every reader of "what does this role hold?", classed

| reader | question | source | class | verdict |
|---|---|---|---|---|
| `OrganizationRoleProvisioner:53` | what should a NEW org's roles hold? | config | **provisioning** | ✅ correct |
| `OwnerInviteService:358,:429` | does this role NAME exist? (`array_key_exists`) | config | **identity** | ✅ correct — never asks what it holds |
| `RolePermissions::isWildcardByDesign()` | is this role top-tier **by design**? | config | **design tier** | ✅ correct — see below |
| `RolePermissionService` (matrix, last-admin, actor privilege) | what does it hold **now**? | DB | security | ✅ correct |
| `OperatorProfile:53` (`getAllPermissions`) | what does the ACTOR hold? | DB | display | ✅ correct |
| every `can()` / `can:` / `@can` | may this actor do X? | DB | security | ✅ correct |
| **`RoleAssignmentService::rolePermissions()`** | what does it hold **now**? | **config** | **security** | ⛔ **THE BUG — removed** |

⚠️ **It was worse than one-directional.** That method fed *both* the role being managed **and** the actor's own
privilege, so an actor whose role had been **narrowed** was judged too powerful (the escalation) and one whose
role had been **widened** was judged too weak (refused work they were entitled to). Both are now correct.

### One source of truth

> ⚠️ **THE DATABASE IS THE LIVE STATE. `config/authorization.php` IS THE SHIPPED DEFAULT.**
> ⚠️ **EVERY SECURITY DECISION READS THE LIVE STATE.**

Stated in the new `App\Support\Authorization\RolePermissions` and in `RoleAssignmentService`'s own class
docblock — the two places a reader arrives. **The config keeps three legitimate jobs, named in code so nobody
tidies them away as dead:** provisioning a new org · which role NAMES exist · and the **design tier**
(`isWildcardByDesign()`), which must *not* read live state — read the database there and narrowing a wildcard
role **once** would unlock it permanently.

**One definition, not two call sites.** `RolePermissions::mapFor()` / `union()` / `isSubset()` are shared by
both services; each service's private readers were **deleted, not moved**, with a comment saying so. Two call
sites querying the same table are still two definitions if each writes its own query — which is exactly how
A-1 happened.

### ⚠️ CAN THE FIX LOCK AN ORG OUT? MODELLED, NOT ASSUMED — **no**

| # | fact | evidence |
|---|---|---|
| 1 | `Property Owner` and `Super Admin` are **permanently** non-editable | `editableRoleNames()` reads the design tier: `editable = false` for both |
| 2 | A role can never be widened past the catalogue | Front Desk widened to **51 of 51**; an invented permission was dropped by the catalog-only intersect |
| 3 | ⇒ **no role can ever exceed a wildcard holder**, who therefore always passes the subset rule | at maximum width, the Property Owner could still assign it (a Group Admin correctly could not) |
| 4 | A non-wildcard actor cannot strip the last wildcard holder | refused: *"You can't assign a role with more access than your own"* — it needs all 51 |
| 5 | Every org gets one at creation | `TenantProvisioningService::FOUNDER_ROLE = 'Property Owner'`, assigned atomically with provisioning |

⚠️ **The brief's stated lockout mechanism is backwards.** *"A role customised down to nothing becomes
unassignable"* — the opposite is true: an empty set is a subset of everything, so a narrowed role becomes
**more** assignable, verified (an emptied `Marketing Manager` is assignable by a Group Admin). The lockout
direction would be a role *widened* beyond everyone, and fact 3 makes that unreachable.

**⚠️ One real hazard the fix DID introduce, and closed.** An unprovisioned role reads back as `[]` — and `[]` is
a subset of everything, so pointing the guard at the database would have made a role the org never had

before, `assignableRolesFor()` offered such a role and `assign()` reached spatie's `RoleDoesNotExist` (a 500);
now it is a clean refusal. It matches the fail-safe `OwnerInviteService::resolveStaffRole()` already had.

### ⚠️ AN INSTRUMENT FAILURE THIS PASS WROTE, AND THE GUARD THAT CAUGHT IT

The new structural guard was first written as

## 0f · THE LAST-ADMIN FLOOR, THEN THE REVOKE CONTROL — 2026-08-30

**Built in that order, in one change.** The floor was written and proven first; only then was the control
added. The reason is that the *absence* of the control was the accidental mitigation for the *absence* of the
floor: `app.roles.revoke` was routed, gated and reachable only by a hand-made POST.

### ⚠️ Does `assign` also remove access? **No — verified against spatie's source, not its name**

`HasRoles::assignRole()` is `$this->roles()->attach(array_diff($roles, $currentRoles), $teamPivot)`. It only
ever **attaches**; it never detaches. So `revoke()` is the single path here that removes a back-office role,
and the floor has one call site. (The matrix's `save()` removes *permissions from a role* and was already
floored for `roles.manage`.)

### ⚠️ "The last admin" means **the last holder of `roles.manage`** — and why

| candidate | verdict |
|---|---|
| **the last member holding `roles.manage`** | ✅ **adopted** — the only capability whose loss is unrecoverable from inside the product. Lose `users.manage` and a role-manager grants it back through the matrix; lose `roles.manage` and nothing can restore it (the matrix route requires it, and `OrganizationRoleProvisioner` runs only at org creation and from seeders). It is also **exactly what `assertNotLastRoleManager` already protected** on the matrix path — same question, same answer, one definition. |
| the last `users.manage` holder | ⛔ rejected — protects a **recoverable** capability, and blocks legitimate restructuring every day |
| the last wildcard (`Property Owner`) holder | ⛔ rejected — too strict: an org that has deliberately given `roles.manage` to a second role should be able to move on from its founder |

**One definition, two hypotheticals.** `RolePermissions::roleManagersAfter($map, withoutRole:, withoutUserRole:)`
computes the survivor set once; the matrix asks *"if role X stopped granting it…"* and revocation asks *"if
user U stopped holding role X…"*. `assertNotLastRoleManager` was rewritten to delegate — the two are not
separate guards. It reads **live state** (the `$map` from `mapFor()` plus spatie membership); a mutation
pointing it at `config/authorization.php` kills 8 tests.

**The three legitimate actions are all still permitted** — removing a departing colleague, demoting someone,
restructuring roles — **whenever another manager remains**, pinned by its own test.

### ⚠️⚠️ THE FLOOR IS CURRENTLY UNREACHABLE ON THE REVOKE PATH — measured, and that is the point

To revoke a role you must hold everything it grants (the subset rule), so **an actor able to revoke a
role-managing role is themselves a role manager and therefore survives**; and you cannot revoke your own role.
Reproduced with two Group Admins as the org's only managers:

```
A revokes B   ACCEPTED  (A still manages — ordinary administration)
A revokes A   REFUSED   "You can't change your own role"                    ← no-self-management
B revokes A   REFUSED   "You can't assign a role with more access than…"    ← the subset rule
primitive: managers left if A loses Group Admin = 0                          ← the floor WOULD fire
```

**The mutation pair characterises it exactly:**

| mutation | outcome |
|---|---|
| force `roleManagersAfter()` to answer "nobody survives" | ✅ **CAUGHT, 7 tests** — incl. the ordinary-administration test and both rendered-page revoke tests, proving `revoke()` **does** execute the floor |
| delete the floor call from `revoke()` | ⚠️ **NOT CAUGHT** — and that is the finding, not a weak test: two older, independent controls refuse first on every reachable path |

So the floor is **belt for a brace that already holds** — built anyway, and explicitly, so that relaxing either
older rule cannot silently reopen the hole. That was the stated goal.

**⚠️ The two rules answer different questions and neither is redundant.** No-self-management asks *"may I
change MY OWN access?"* — refused even when ten other managers exist. The floor asks *"would the ORGANISATION
still have someone able to manage access?"* — it fires against any target. The no-self-management rule is
**not** made redundant and was not touched.

**⚠️ Reported, not changed:** the floor counts *holders*, not sign-in ability — a member whose `users.status`
is `inactive` still counts. That is the semantics `assertNotLastRoleManager` has always had, and no operator
route deactivates a back-office user today, so it is not currently reachable from `/app`. Widening it is a
separate decision.

### ⚠️ The control — proven from a RENDERED PAGE, then followed

`resources/views/livewire/operator/operator-roles.blade.php`, section `id="revoke"`, immediately after the
assign form — because the page's own copy points there. Gated exactly as the route is (`users.manage`) and
narrowed to roles the actor may actually manage, so it cannot invite a refusal it could have predicted.

**No JavaScript**: the confirmation is a native `<details>`, so it works where Alpine does not and a
server-side test can read it. The confirmation names **who loses what**:

> **Finn Desk** will lose the **Front Desk** role and everything it grants. They keep any other roles they hold.

The test **fetches `/app/roles`, locates the form, reads `_token` / `user_id` / `role` out of the markup, and
posts exactly those** — the H-2 precedent; asserting the route works would prove nothing, because the route
always worked. **Live-fetched** against the running server as `demo-admin`: 3 forms, **3 distinct per-row
password ids** (`revoke_pw_<ulid>-<role-slug>`), 3 confirmations, and the actor's own row correctly showing
*"Ask another administrator to change your own roles."* instead of a control.

### The page's promise, quoted — and now true

`operator-roles.blade.php:173` has always said:

> "The back-office role catalogue is fixed. To take access away from a role, un-toggle its permissions above;
> **to move a person off a role, revoke it from them in the assignment section — they keep their other roles.**"

Both halves are now real: the control lives in that section, and a test proves a user holding two roles keeps
the other. **Swept the rest of the Roles page:** every remaining sentence names something reachable; the

### ⚠️ WHERE THE BRIEF WAS WRONG

**"Build the button first and you hand every administrator a way to empty their own organisation"** — verified
**false**. Even with no floor at all, the subset rule and no-self-management make emptying the org unreachable

## 0n · REMOVAL NOW ENDS THE TEAM'S ACCESS — AND THE MODAL STOPPED LYING — 2026-08-31

### 1 · What a sub-user could still reach and do — and the fact that decides the severity

Measured with the widest sub-user role (co-owner) and the removal run FIRST, so nothing could be memoised:

```
owner trashed = true · sub-user owner_users row = 'active'
GET /owner → 200
/owner/units mentions the real unit code 'U1' → NO — an empty shell
WRITE payout preferences → rows 0 → 1   ⚠️ THE WRITE LANDED
```

⚠️ **Reads were harmless; the WRITE was not.** Every portal page returned 200 but rendered **no data** — the
data models' scope excludes a soft-deleted owner, so nothing leaked: no units, no bank details (neither the
masked last4 nor the IBAN), no statements. **But a payout-preference write — pausing payouts, setting a
minimum — landed on the removed owner.**

**The mechanism, from the source:** `OwnerContext` resolves primary ownership through `Owner::query()`
(`:241`, soft-delete scope applies, correctly excluded) but resolves sub-memberships from **`OwnerUser::query()`
alone** (`:247`) — **no join to `owners`** — so a row pointing at a trashed owner still resolved. A read needed
the owner's *data* and got nothing; a write needed only the owner's *id* and went straight through.

⚠️ **So this was READ-neutral and WRITE-live, and the write is money-adjacent.** A read-only check would have
called it harmless.

### 2 · Whose are the sub-users? **Unambiguous — the owner's**

| | |
|---|---|
| writers of `owner_users` | **exactly one** — `OwnerTeamInviteService:154` |
| reachable from | `/owner/team/invite` → **`EnsurePrimaryOwner`** — the owner's own action |
| operator paths that write `owner_users` | **none.** `OwnerInviteService` (operator → owner) never touches the table |
| routes that can REMOVE a sub-user | `owner.team.members.remove` — **also `EnsurePrimaryOwner`** |

⚠️ **That last row settles the design question.** Once the primary owner's login is deactivated, **nobody can
close the access**: the operator has no route, and the only person who could is locked out. **"Require a second
explicit action" was not an available option**, which leaves only cascade or an honest admission of an
unclosable hole.

### 3 · The copy — corrected, and read from the rendered page

Before: *"Portal access ends immediately"* — false. Now, live-fetched from `/app/owners/{id}`:

> · Portal access ends immediately — for **Demo Owner** and **everyone on their team** (2 people)
> · Anyone on the team who also works for you **keeps their own login** — only their access to this owner ends

The count is real (`owner_users` active, per owner) and the demo owner genuinely has two. **Swept the rest of
the owner-management copy** — no other claim about what removal does. **Nothing named that does not exist:**
the second line describes a rule that is actually enforced, not a route being promised.

### 4 · The cascade — implemented, because the answer was unambiguous

**Options considered:**

| option | cost |
|---|---|
| **cascade** (chosen) | risks cutting off someone the operator invited — ⚠️ **except it cannot**: `OwnerLoginLifecycle` disables a login only when the person has no other sub-user link, no Owner of their own, **and no back-office role**. A staff member keeps their account; only the owner link ends. Proven by test. |
| require a second explicit action | ⛔ **impossible** — the only removal route is primary-owner-only and that person is locked out |
| a choice at the point of removal | more UI, and the "leave them" branch is the unclosable state above |
| copy-only | would have to say *"their team keeps access and you cannot end it"* — honest, but leaves a money-adjacent write open |

⚠️ **REVERSAL, stated plainly:** there is **no un-archive route**, so a cascaded sub-user cannot be restored
through the product — but that asymmetry **already existed** for the primary owner, whose login this action has
always disabled irreversibly. The cascade adds no new one. Both rows are soft-deleted, so the data is
recoverable by a developer; the *product* offers no way back. **Reported, not built** (an un-archive route is
its own decision).

**Implementation matches how an owner removes a member themselves** — `->delete()` (soft), *"the owner scope no
longer resolves them"* — and `disableIfOrphaned` was **moved, not copied**, into `App\Support\Owner\OwnerLoginLifecycle`,
because a second copy of "may this login be disabled?" is exactly the drift §N.8f forbids.

### 5 · Archived means **GONE**, not paused — so the residual access was a real gap

| check | result |
|---|---|
| any operator surface reading a trashed owner (`withTrashed`) | **none** — platform, payouts, reports, Livewire |
| payout runs | `PayoutRunService:191,202` use `Owner::query()` → a removed owner is **excluded** |
| what the code states | *"a careful **ARCHIVE-not-destroy**"*, *"Statements/payouts/ledger are RETAINED (no cascade)"*, audited `owner.archived` |

**So the relationship ends everywhere an operator looks, and only the financial record survives.** Nothing
suggests "paused", so the residual portal access was not intentional.

### 6 · Mutations — three, all caught

| mutation | died |
|---|---|
| the cascade removed | **3** — the write test, the membership test, the staff-safety test |
| the safety limit removed (disable everyone) | the staff-login test — **the whole risk of a cascade, pinned** |
| the false copy restored | the rendered-copy test |

⚠️ Tests assert on **data**, not status codes: the old behaviour also returned 302 on that write. And they use
`withTrashed()` — a plain query would report the row absent whether or not the cascade ran, and
`withoutGlobalScopes()` would report it present either way.

### Where the brief was wrong

1. **"a gap someone knows about gets worked around"** — here the operator *couldn't* work around it: no route
   exists for them, and the only person who had one was locked out.
2. **"read access, write access, or both"** — it was **write-only in effect**: reads returned empty shells.
   A read-focused assessment would have understated it.
3. **"if the operator invited them, deactivating them silently would be a surprise"** — the operator cannot
   invite them at all, and the existing orphan rule already protects anyone holding a back-office role.

## §0o · G1 — THE LAST-ADMIN FLOOR COUNTED HOLDERS, NOT PEOPLE WHO CAN SIGN IN

**Verdict: the definition was NOT ambiguous, the floor WAS wrong, and it is now fixed — but the worst thing
this pass found is NOT closed by that fix.** Read §0o.3 before §0o.2.

### §0o.1 · The five candidate definitions, settled by measurement

The brief asked which of five states should count as "cannot sign in". Four of them are the same state, one
cannot exist, and one is already handled — so there was nothing to adjudicate.

| Candidate | Measured | Verdict |
|---|---|---|
| Deactivated (`inactive`) | `LoginRequest::authenticate()` folds `status = active` into the credential query | **blocks sign-in** |
| Invite never accepted | `OwnerInviteService:121` writes `status = 'invited'`; `:287` writes `'expired'` | **same column, same rule** |
| Orphan-disabled | `OwnerLoginLifecycle:42` writes `status = 'disabled'` | **same column, same rule** |
| No password set | `users.password` is `NOT NULL` in the create migration | **cannot exist** |
| Soft-deleted user | `User::role()` is an Eloquent query, so `SoftDeletingScope` applies — measured: a soft-deleted holder is already excluded | **already correct, for free** |
| *(org suspended — the sixth)* | `CustomerController:86` writes `organizations.status`; `LoginRequest` never reads it | **a different axis; not a sign-in gate** |

⚠️ **So "can sign in" has exactly one operative meaning: `users.status === 'active'`** — because that is
literally the value the login query requires. The apparent five-way choice was one column with five writers.

### §0o.2 · The fix

`RolePermissions::roleManagersAfter()` counted permission **holders**. It now counts holders **who can sign
in**, filtered by the same rule the login query applies.

⚠️ **One definition, not a second.** `User::SIGN_IN_STATUS` is now the single source, read by all three
places that asked the question — the floor, `LoginRequest::authenticate()`, and both
`PasswordResetController` broker lookups. Each of the three is **mutation-proven separately** (removing the
floor's filter kills only the new floor test; removing login's kills only the inactive-login test; removing
the reset lookups' kills only the invited-account test), so the constant is load-bearing at every site rather
than decorative at two of them.

**Where the floor actually bites — recorded so nobody re-derives it:** on the **matrix**, not on revoke. A
revoking actor must themselves hold `roles.manage`, and self-management is separately refused, so a revoke
always leaves the actor standing and the survivor count cannot reach zero. Stripping the permission from a
**role** can empty it. `Property Owner` is wildcard-by-design and refused by the matrix outright, so the
reproduction needed two *editable* manager roles.

**The stricter floor does not block ordinary administration.** It refuses only when the result would be zero
sign-in-able managers — which is exactly the state that must be refused. Two tests pin the permissive side
(an ordinary strip and an ordinary revoke both still succeed).

### §0o.3 · ⚠️⚠️ WHAT THIS DOES **NOT** CLOSE — an organisation can still be locked out

**Modelled end to end, and reachable today:**

```
role-managers before: 1   (Dana holds roles.manage)   Dana can sign in: true
Ada (Group Admin: users.manage, NOT roles.manage) runs app.owners.remove on the owner Dana is linked to
AFTER removal — Dana status: inactive
  floor counts (HOLDERS): 1
  of those, able to SIGN IN: 0     ⚠️ THE ORG CAN NO LONGER MANAGE ACCESS
```

⚠️ **Widening the floor does not prevent this, and it was never going to.** `roleManagersAfter` /
`assertNotLastRoleManager` are consulted by exactly two callers — `RolePermissionService:175` and
`RoleAssignmentService:181`. **`OwnerManageController` has zero occurrences of either.** The removal path
deactivates a back-office login *without ever asking the floor*. A floor is a guard on the paths that consult
it; this path does not.

⚠️ **And it is unrecoverable from inside the product.** The password-reset broker's lookup is scoped to the
same `status = active`, so the locked-out holder cannot even request a reset; and after removal the `Owner`
is soft-deleted, so `Owner::query()->findOrFail()` 404s and the portal-active toggle that would reactivate
them is out of reach. Recovery is the console procedure written in §0h — `docs/GO-LIVE-RUNBOOK.md`, "Incident · a role has lost
permissions" — which needs a human with shell access.

**Severity is bounded, not dismissed.** `TenantProvisioningService` gives the founder the `Property Owner`
**role** and does not create an `Owner` record, so the dual shape (sole role-manager *and* an owner's linked
user) is unusual rather than the default. ⚠️ **But the demo org has exactly one role-manager**, so the margin
is one.

**Left in place, reported, not fixed** — per the standing instruction that each boundary gets its own pass
with its own proof. The fix belongs on the removal path, not in the floor.

### §0o.4 · ⚠️ A CORRECTION TO THE BRIEF

The brief stated the floor had been unreachable until `OwnerLoginLifecycle` shipped. **That is false.**
`OwnerManageController:240` has always set the removed owner's linked user to `inactive`. The trigger did not
arrive yesterday; it has been there the whole time, and the floor has been countable-but-wrong for as long as
it has existed.

### §0o.5 · The load-bearing dependency, pinned rather than commented

`OwnerLoginLifecycle::disableIfOrphaned()` spares a user who still holds a back-office role (`$hasRole`).
That one clause is what stops the **cascade** from becoming a *second* path to the same lockout.

`LastRoleManagerSurvivesTheCascadeTest` pins it in both directions: removing the exclusion goes RED (3 tests
die), and neutering the cascade entirely also goes RED (4 die) — so the pin cannot be satisfied by a cascade
that simply never disables anyone. It drives a real **write** (the surviving manager actually edits the
matrix afterwards), because `status === 'active'` alone would have proved only half of it.

### §0o.6 · ⚠️ AN ERROR I MADE, AND THE LESSON

Keying the two auth files to the new constant, **the `use App\Models\User;` import silently failed to land in
`LoginRequest`**, leaving an unqualified `User` that PHP resolved to `App\Http\Requests\Auth\User`. The
login route 500'd.

⚠️ **`php -l` reported "No syntax errors detected".** Lint parses; it does not resolve class references. I
recorded "✅ all three parse" and moved on — a false green of my own making.

⚠️ **It surfaced only because a mutation caught *too much*.** Removing an unrelated filter appeared to kill
ten tests including the login suite, which is not a credible blast radius for a floor filter. **The
over-broad catch was the signal.** Investigating it — rather than banking a satisfying "✅ CAUGHT (10 died)"
— found the breakage. The standing rule is *disbelieve a clean mutation*; this pass adds its mirror:
**disbelieve a mutation that catches more than it could plausibly reach.** M3/M4/M5 were re-run clean
afterwards, and each now kills exactly one precise test.

Every file touched in this pass is now checked with `class_exists()`, not `php -l`.
