# Trusted hosts, forwarded headers and HTTPS

**2026-09-04.** ⚠️ **Most of this was already built.** The brief asked whether `TrustHosts` is registered
"at all" and treated the proxy configuration as absent. Both exist, are reasoned in place, and carry tests.
What was missing was narrower — and it is the half the brief itself called *"worth more than the fix"*.

## #1 · Everything that decides the scheme and host, and which wins

| input | today | who wins |
|---|---|---|
| `APP_URL` | `http://localhost:8000` | ⚠️ **decides everything** — see below |
| `ASSET_URL` / `config('app.asset_url')` | **unset** | `asset()` falls back to the root url ⇒ same-origin by construction |
| the `Host` header | pinned to `APP_URL`'s host by `trustHosts()` | refused if it does not match (production only) |
| `X-Forwarded-Proto` / `-Host` / `-Port` | **ignored** — `TRUSTED_PROXIES` is empty | trusted only when the sender is a named proxy |
| `URL::forceRootUrl(config('app.url'))` | active whenever `APP_URL` has a host | ⚠️ **overrides the request entirely** |
| `URL::forceScheme('https')` | when `config('security.force_https')` (defaults to `APP_ENV === production`) | overrides the scheme |

⚠️ **The request does NOT decide the host — `APP_URL` does.** `forceRootUrl` was added as the host-header
poisoning fix (audit H-1), and it has a second consequence the brief did not anticipate: because generation
goes through the forced root in **both** a web request and a queued job, an emailed link and a web-generated
link cannot disagree. The classic "email points at localhost" split is structurally closed — and replaced by
a single dependency: **if `APP_URL` is wrong, every link is wrong at once.**

**Absolute URLs elsewhere:** the sitemap and the JSON-LD structured data both emit absolute URLs, and both
build them through `url()`/`route()` — so they inherit the forced root and cannot drift from it. No
hardcoded host was found in a view or a mail template.

## #2 · Which proxies, and what the server must guarantee

`config('security.trusted_proxies')` is **empty** — trust nothing, which is the safe default and what ships
today. `AppServiceProvider::boot()` sets `TrustProxies::at()` and `withHeaders()` **only when it is
non-empty**, via the statics (not `bootstrap/app.php`, which runs before `config` exists, and not a
subclass, which the framework's own middleware would reset — both recorded in place, both learned by
getting it wrong).

⚠️ **What a forged header could do here, concretely:** with a trusted proxy configured, `X-Forwarded-Host`
would set the request host. The password-reset mail is rendered **inside the request**, so before
`forceRootUrl` existed a forged host put the attacker's domain into the victim's email **with a valid reset
token**. That is reproduced in `HostHeaderPoisoningTest`. Today `forceRootUrl` makes the link independent of
the request, so the concrete harm is closed even with `TRUSTED_PROXIES=*` — but the isolation requirement
below still matters for the IP allowlist and the per-IP rate limiter, which read `Request::ip()`.

**Written into go-live:** the app must be **unreachable except through the proxy**, or a forged
`X-Forwarded-For` defeats the operator IP allowlist and per-IP throttling.

## #3 · Trusted hosts, and the CSP

`trustHosts()` **is registered** in `bootstrap/app.php`, derived from `APP_URL`'s host, `subdomains: false`.
⚠️ It is **inactive outside production** (`TrustHosts::shouldSpecifyTrustedHosts()`), which is why the suite
proves the root-url half instead — recorded in the registration itself.

⚠️ **The CSP names no host at all.** It is `'self'` throughout — `default-src`, `script-src`, `connect-src`,
`img-src`, `frame-ancestors`, `form-action`, `base-uri`. So there is no allow-list to keep in agreement with
`asset()`; the requirement is simply that **`asset()` stays same-origin with the document**. That is exactly
what the earlier incident broke: a port mismatch made assets cross-origin and `'self'` refused every script.

⚠️ **NOTHING ENFORCED THAT, AND NOW SOMETHING DOES.** Two new guards:

- `asset()`'s origin must equal `url()`'s origin;
- if `ASSET_URL` is ever set, it must share `APP_URL`'s origin.

**This is the deliverable the brief predicted would be worth more than the fix** — there was no fix to make,
only an unguarded invariant.

## #4 · Every signed route, and what a failure costs

| route | generated by | who receives it | cost of failure |
|---|---|---|---|
| `guest.claim.verify` | `GuestAccountService` | a guest claiming their booking | ⚠️ **first contact** — they cannot get in, and simply leave |
| `owner.account.email.verify` | `OwnerAccountController` | an owner changing their login email | locked to the old address |
| `admin.account.email.verify` | `AdminAccountController` | the platform admin | same |
| `login-approval.approve` | `LoginController` | an operator/owner approving a login | cannot sign in |
| `marketing.unsubscribe` (+ `.confirm`) | `MarketingUnsubscribe` | a guest opting out | ⚠️ cannot unsubscribe — a compliance problem, not an inconvenience |

⚠️ **A signature is host-sensitive — measured, not assumed.** A link signed for
`https://not-our-host.example` returns **403** here, while a correctly-signed one returns 200, and a
tampered signature or a swapped parameter also returns 403. The user sees only *"this link is invalid"*,
which is indistinguishable from genuinely expired.

⚠️ **The queued-job case is closed by the same mechanism.** A job has no request and generates from
`APP_URL`; a web request verifies against the same forced root. They agree by construction — which is why
`APP_URL` being exactly the canonical origin is the single point everything rests on.

## #5 · Local development

Unchanged and proven: `url()` and `asset()` both start `http://localhost`, `force_https` is false, `/login`
returns 200, and a request with no forwarded headers infers nothing. The suite is unaffected — the whole run
is green with no scheme-dependent assertion moved.

## #6 · Forcing the scheme — the smaller change was already the one in place

`forceScheme('https')` is **already** guarded on `config('security.force_https')`, which defaults to
`APP_ENV === 'production'` **and is overridable by `FORCE_HTTPS`** — so a staging environment behind TLS can
enable it without pretending to be production. That is precisely the honest condition the brief asked for,
and it follows the `StripeSafetyGuard` shape (a config-driven guard, not an environment literal).
**Nothing was added.**

## #7 · What is proven, and what is not

**Proven here:** forged `X-Forwarded-*` are ignored from an untrusted sender and honoured from a trusted
one, through the application's own middleware and mask · a proxy list that names a *different* address still
ignores them · `asset()` is same-origin · `ASSET_URL` cannot silently point elsewhere · the CSP names no
external origin · a foreign-root signature is refused · local development is unchanged.

**Not proven, and listed in `GO-LIVE-REQUIREMENTS.md`:** that a real proxy sends the headers · that TLS
terminates where expected · that the CSP survives the proxy unmodified · that the certificate covers the
canonical host.

## #8 · Mutations, and two instrument findings

| mutation | landed | result |
|---|---|---|
| **wrong fix** — trust ALL proxies (`TRUSTED_PROXIES=*` default) | ✅ | **RED** |
| `ASSET_URL` at a foreign origin — the exact incident | ✅ | **RED** |
| stop forcing the root url | ✅ | **RED** |
| force https unconditionally (breaks local) | ✅ | **RED** |
| remove `HEADER_X_FORWARDED_PROTO` from the mask | ✅ | ⚠️ **GREEN — a no-op, not a gap** |
| remove the proto bit *genuinely* (proto **and** AWS_ELB) | ✅ | **RED** |

⚠️ **The proto-line mutation is a no-op and the arithmetic says so.**
`HEADER_X_FORWARDED_AWS_ELB = 26 = FOR|PROTO|PORT`, so it **already contains** the proto bit: the mask is
**30 with the line and 30 without it**. Deleting it changes nothing. That is a redundant line in the source,
not a hole in the test — and removing the bit for real goes red.

### ⚠️ Two instrument findings, both of which would have made this pass worthless

1. **A `Host` header cannot be forged through the test client.** `get($uri, ['Host' => …])`,
   `withHeaders()`, `withServerVariables(['HTTP_HOST' => …])` and `call()` with server parameters **all**
   still report `localhost` — the harness pins the host from `APP_URL`. A proxy test written that way
   asserts nothing. Only a raw `Request::create()` forges it. (The forwarded headers themselves *do* arrive
   and are correctly ignored, so the existing `SecurityHeadersTest` assertion is sound.)
2. **`isSecure()` re-evaluates against the CURRENT static trust state.** The first version of the helper
   restored the trusted proxies in a `finally` and asserted afterwards — reading `false` regardless of what
   the middleware had done. The facts must be captured *inside* the trusted scope.

⚠️ And the trusted-half helper originally supplied **its own header mask**, which made it prove itself:
the mask must come from the application's configuration, reached by setting `security.trusted_proxies` and
re-booting the provider.

## ⚠️ Where this brief was wrong

It asked to "establish whether `TrustHosts` is registered at all" and to find the honest middle for trusted
proxies as if neither existed. **Both are built, tested and documented**, along with `forceRootUrl`,
`forceScheme`, `config/security.php`, `.env.example` entries and go-live items B14/B16. It also expected the
CSP to name a host that `asset()` must match — **the policy names no host at all**, so the invariant is
same-origin rather than agreement with a list. And it warned that a queued job's `APP_URL` might disagree
with a web request's host: `forceRootUrl` makes them agree by construction.
