# Vyrobel — application audit in a real browser · 2026-09-02

**The first time any authenticated realm has been driven by a browser.** Five realms, seven demo accounts,
**~150 authenticated screen loads** at 1280×900 and 375×812.

**Instrument.** `chrome-headless-shell` over CDP (the Playwright/chrome-devtools MCP servers cannot launch in
this environment — the GPU helper is blocked). Real form login per realm, never a faked session. Console,
network, layout and heading structure captured per navigation on the `APP_URL` origin against a warmed
`php artisan serve`.

⚠️ **Instrument validated before use:** a page that must emit a console error produced both the
`console.error` and the uncaught `ReferenceError`; a clean page produced neither.

⚠️ **Nothing was fixed. No test was added. No file was changed.**

## 1 · ⚠️⚠️ Does a PWA exist? **NO — and a shipped document says it does**

**Established, not assumed:**

| Looked for | Found |
|---|---|
| a web app manifest | **none** — the only `manifest.json` files are Vite asset maps under `public/build/` |
| `<link rel="manifest">` | **zero** occurrences in `resources/views/` |
| a service worker / registration | **none** — no `sw.js`, no `serviceWorker.register` anywhere |
| `apple-touch-icon`, `theme-color`, `beforeinstallprompt` | **none** |
| a PWA package | none in `package.json` or `composer.json` |

**There is no PWA, partial or otherwise.** Nothing can be installed and nothing works offline — so the
"worse than none" case (an installable app that breaks offline) **does not arise**. That is the good news.

⚠️⚠️ **AND IT CONTRADICTS A RECORDED FACT.** `CLAUDE.md:3` — the auto-loaded project memory every session
inherits — describes the product as *"PMS + channel manager + booking engine + **guest/staff PWAs** + owner
portal + AI agents"*. **There are no PWAs.** `docs/STATE.md`, `KNOWN-LIMITS.md` and
`GO-LIVE-REQUIREMENTS.md` make no PWA claim, so the error is isolated to the one file that is loaded first
and trusted most.

**What a PWA would require** (so the size of the gap is known, not built): a manifest with name/icons/
`display`/`start_url`; a service worker with an explicit caching strategy; icons at several sizes; an
offline fallback; HTTPS (already a go-live item); and a decision about **what is safe to cache** — this app
shows guest PII and money, so an offline cache is a data-protection question, not just an engineering one.

⚠️ **Where it would actually matter: the housekeeping board** (a housekeeper in a corridor). Today
`/app/housekeeping` is a normal server-rendered page: **lose the network and it is a browser error page.**

## 3 · ⚠️⚠️ HIGHEST CONSEQUENCE — the operator back office is unusable on a phone

**29 of the 31 screens a Hotel Manager can reach overflow horizontally at 375px — by 379px to 986px.**
The page is roughly two to four times the viewport width. Measured, per screen:

| screen | overflow | screen | overflow |
|---|---|---|---|
| `/app/rates` | **986px** | `/app/housekeeping` | **495px** |
| `/app/notification-preferences` | 634px | `/app/reservations` | 474px |
| `/app/dashboard` | **624px** | `/app/front-desk` | 439px |
| `/app/maintenance/settings` | 593px | `/app/calendar` · `/app/rack` | 418px |
| `/app/schedule` | 555px | `/app/units` | 379px |

Only `/app/billing` and the other 403 pages are clean — because they render an error page.

### The cause is ONE shared shell, and it is two lines

A phone breakpoint **does exist** — `operator.blade.php:1634` — so this is not "nobody built a mobile
layout". Two properties defeat it:

1. **`operator.blade.php:1635`** — the mobile rule is `.vy-shell { grid-template-columns: 1fr; }`, while the
   desktop rule at **line 129** correctly reads `230px minmax(0, 1fr)`. A bare `1fr` is `minmax(auto, 1fr)`,
   and that `auto` minimum is a **min-content floor the track cannot shrink below**.
   ⚠️ **This is the same defect class as the marketing footer grid fixed on 2026-09-02** — a new instance in
   a new place.
2. **`div.vy-topbar-actions`** measures **629px** and neither wraps nor shrinks.

**🔬 Proven by live experiment, not reasoning** (injected CSS, removed again, no file touched):

| screen | as shipped | with `minmax(0,1fr)` | remaining floor |
|---|---|---|---|
| `/app/dashboard` | 999px | **651px** | topbar actions |
| `/app/rates` | 1361px | **651px** | topbar actions |
| `/app/reservations` | 849px | **651px** | topbar actions |

Both must change; either alone leaves the page ~1.7× too wide.

⚠️ **The housekeeping board — the one screen with a real mobile use case — overflows by 495px.** Its phone
layout was changed and never seen on a device; **this is the first sighting, and it does not work.**

## 5 · The guest realm — measured for the first time

**13/13 screens load. Zero console errors. Zero horizontal overflow at 375px.** The guest realm is
**properly responsive where the operator realm is not**, and far lighter: 10–47kB against the operator's
205–346kB.

### ⚠️ Isolation holds — verified after correcting my own probe twice

**12 of 12 foreign-reservation URLs return 404** to a logged-in guest — the reservation detail, the arrival
page (door codes / wifi) and online check-in, across four reservations belonging to other guests.
**Nothing leaked.** See §8 for the two probe errors I made before getting this right.

### ⚠️ NEW FINDING — 7 of 13 guest screens have no headings at all

Not merely no `<h1>` — **no heading elements whatsoever**: `/guest/trips`, `/guest/account`,
`/guest/home`, `/guest/messages`, `/guest/notifications`, `/guest/payments`, `/guest/saved`, `/guest/wallet`.

Every *unauthenticated* guest screen (login, claim, forgot-password, help) has exactly one correct `<h1>`.
So the defect is confined to the signed-in surfaces — the ones a guest actually lives in. A screen-reader
user navigating by heading gets nothing on any of them.

⚠️ **New instances of a known class** (the marketing `/contact` zero-`h1` defect, fixed earlier), in a realm
where it had never been looked for. `/book/seaside-demo/checkout` has the same shape: **zero `<h1>`**.

## 6 · ⚠️ Seven operator screens carry no permission gate

These have **only `EnsureSubscriptionActive`** — no `can:` middleware — so any authenticated back-office
user reaches them regardless of role:

`/app/front-desk` · `/app/rack` · `/app/calendar` · `/app/maintenance` · `/app/email-templates` ·
`/app/unit-requests` · `/app/notifications`

**Concretely:** `demo-housekeeper` holds four permissions (`units.view`, `housekeeping.view`,
`housekeeping.manage`, `schedule.view`) and can nevertheless read the **front desk arrivals board**, the
**full reservation calendar and rack**, and the **maintenance work queue**.

⚠️ **Bounded, and stated precisely:** this is *within one tenant*, to that tenant's own employee, and
invariant #28 keeps those surfaces name-only, so **no guest contact PII is exposed**. It is a role-boundary
question — whether a housekeeper should see the whole reservation grid — **not a data leak**. Reported for
a ruling, not as a breach.

## 7 · Smaller findings

- **`/app` returns 404.** There is no index route; the dashboard is `/app/dashboard`. Harmless unless
  something links to `/app` — worth a redirect.
- **`/app/schedule/pdf` returns an HTML page** (286kB, 81 focusables — identical to `/app/schedule`), not a
  PDF document. Either it renders an HTML preview by design or the route resolves to the wrong response;
  **not established which**.
- **`demo.traveller` has `claimed_at = NULL`** while `CLAUDE.md` calls it *"a claimed, booking-tied guest
  account"*. Login works regardless, so the description is loose rather than the behaviour wrong.
- **`reservation_guests` holds 0 rows in the entire database.** The guest↔reservation link is
  `reservations.lead_guest_id`. A pivot table that exists and is never populated is worth a decision.

## 8 · False positives — including three of my own probe errors

1. **"`/app/channels` is 403 for every role, including the 51-permission account."** Not a permission
   defect: it is gated by `EnsurePlanFeature:channels`, and `planAllows('channels')` returns **false**
   because the demo org is on Essential. **The plan gate working correctly.**
2. **"10 platform-admin URLs return 200 anonymously."** My driver **follows redirects**, so it recorded the
   login page's 200. Raw HTTP shows `/admin`, `/admin/customers`, `/admin/plans`, `/admin/activity`,
   `/admin/integrations` all **302 → `/admin/login`**. The realm is properly gated.
3. **"The demo guest owns zero reservations."** I queried `reservation_guests` (0 rows, always). They own
   **three**, via `reservations.lead_guest_id`.
4. **"A guest opened three reservations that are not theirs."** They *were* theirs — see (3). The corrected
   probe on four genuinely foreign reservations returned 404 twelve times out of twelve.
5. **"29 operator screens each overflow."** They share **one** cause in the shell, not 29 separate ones.
